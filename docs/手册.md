## 2. 功能详解

- **TCC 三件套**：`Reserve`（一次可带多个 `(product,warehouse,qty)` 项，一个事务内全部成功或全部失败）→ `ConfirmIssue`（转实际出库，一项一条流水）或 `CancelReservation`（释放）。`GetReservationStatus` 全程只读，专门防"薛定谔的超时"（§4.5）。
- **幂等**：`Reserve`/`CancelReservation`/`ConfirmIssue`/`Receive`/`Adjust` 五个写命令共用 `command_idempotency` 表，走"先原子声明（`INSERT ... ON CONFLICT DO NOTHING`）再做事"的 claim-first 模式——比"先查后插"更强：两个带同一个 `idempotency_key` 的并发请求，后到的那个会被数据库锁挂起直到先到的事务提交/回滚，不会出现"两边都以为自己是第一次"的窗口（`backend/internal/repo/pgerr.go`、`repo.go` 的 `claimIdempotency`/`finalizeIdempotency`）。
- **防超卖**：判定与加锁是同一条 `UPDATE ... WHERE on_hand_qty - reserved_qty >= $1` 语句（§2.2）。`Adjust` 用同样的思路把"不能调到负库存/低于已预留量"也写进 `WHERE`。
- **事件**：`Receive`/`ConfirmIssue`/`Adjust` 都发 `erp.inventory.adjusted.v1`（`aggregate_id` 是 `movement_id`，`version` 恒为 1——每条流水都是只出现一次的新聚合根）。消费 `mdm.product.created.v1`/`.updated.v1` 维护 `product_tracking_snapshots`（本阶段第一次真的在组件里用 `besdk.Consume`，见 §6 排障）。
- **后台循环**（`module.go` 的 `Start`，四个并发跑）：Outbox 推送 + 周分区维护（`event_outbox`/`event_inbox`）+ 月分区维护（`inventory_movements`，`backend/internal/partition/monthly.go`）+ 消费 `mdm.product` 事件。

## 3. 完整契约清单

**gRPC `erp.inventory.v1.InventoryService`**（9 个 rpc，见 `contracts/erp/inventory/v1/inventory.proto`）：

| rpc | 类型 | 暴露到 REST？ |
|---|---|---|
| `Reserve` / `CancelReservation` / `ConfirmIssue` | 写，TCC 三件套 | ❌ 组件间协议，不是人类操作 |
| `GetReservationStatus` | 读 | ❌ 同上；区分 `NOT_FOUND` 与 `CANCELLED`（防"薛定谔的超时"） |
| `Receive` / `Adjust` | 写 | ✅ `/erp/inventory/movements/receive`、`/movements/adjust` |
| `GetBalance` | 读 | ✅ `/erp/inventory/balances` |
| `BatchGetBalance` | 读 | ❌ 只给组件间 gRPC 客户端防 N+1 用 |
| `ListMovements` | 读，游标分页 | ✅ `/erp/inventory/movements` |

**发布事件：** `erp.inventory.adjusted.v1`（`Receive`/`ConfirmIssue`/`Adjust` 都发）、`erp.inventory.transferred.v1`（占位，阶段二不实现）。
**消费事件：** `mdm.product.created.v1` / `.updated.v1`（只取 `tracking_type` 维护摘要副本）。

详细字段与判据见设计计划 `docs/design/erp-inventory.md` §3、§4——那份是真相源，这里是速查表。

## 4. 数据模型

| 表 | 分区 | 唯一约束 / CHECK | 说明 |
|---|---|---|---|
| `warehouses` | 不分区 | `code` 唯一 | 主数据。**没有管理接口，迁移播种**（`003_seed_warehouses`：`WH-EAST`/`WH-SOUTH`），见设计计划 §9 第 5 条 |
| `inventory_balances` | **不分区**（§11.2.5 热点表） | `(product_id, warehouse_id)` 唯一；`CHECK on_hand_qty>=0 AND reserved_qty>=0`；`CHECK reserved_qty<=on_hand_qty`（数据库层兜底，物理防线是条件更新，见 §2.2） | 当前余额，防超卖判定点 |
| `inventory_movements` | `created_at` **月**分区 | `CHECK reason IN (...)`；`CHECK serial_no='' OR abs(qty)=1` | 只增不改。`(product_id, warehouse_id, created_at)` 与 `(warehouse_id, created_at)` 两个查询索引 |
| `inventory_reservations` | 不分区 | `(reservation_id, product_id, warehouse_id)` 唯一；`CHECK qty>0`；`CHECK status IN ('RESERVED','CONFIRMED','CANCELLED')` | **一行 = 一个预留项**，`reservation_id`（`inventory_reservation_seq` 序列取号）是同一次 `Reserve` 调用的分组键，见设计计划 §9 第 6 条 |
| `product_tracking_snapshots` | 不分区 | `product_id` 主键 | `mdm-product` 的摘要副本，只有 `tracking_type` + `version` |

`warehouse_id` 是 `inventory_balances`/`inventory_movements`/`inventory_reservations` 三张表上真实的本 schema 内外键（`REFERENCES warehouses`）；`product_id` 全部是 `TEXT` 不透明外键，不建 FK（设计计划 §5：本组件不依赖 `mdm-product`）。

另有全组件通用的 `event_outbox`/`event_inbox`（周分区）+ `command_idempotency`（Reserve/CancelReservation/ConfirmIssue/Receive/Adjust 五个写命令共用一张幂等表）。

**实测验证**（Task 9，`erp_inventory_test` schema 里真跑过）：条件更新防超卖（7 件成功、紧接着 5 件因超额被拒且 `UPDATE 0`）、唯一约束拒重复 `(product_id, warehouse_id)`、序列号 CHECK 拒 `qty≠1`、`reason` CHECK 拒非法值、直接 `UPDATE` 破坏不变式被 `no_oversell` CHECK 拦下、新流水行正确路由进 `inventory_movements_2026_09_01` 分区、up/down 迁移在空数据下可完整往返。

跑测试前必须先用真的迁移工具把 `erp_inventory` schema 建出来（测试连的是真库，不是 mock）：

```bash
export DATABASE_USER=postgres DATABASE_PASSWORD=<密码> DATABASE_HOST=localhost DATABASE_PORT=5432 DATABASE_NAME=brickkit_test_db PG_SCHEMA=erp_inventory
go run ./backend/cmd/migrate
```

**核心测试**是 `backend/internal/repo/repo_test.go` 的 `TestReserve_并发防超卖`：100 个 goroutine 并发抢 30 件库存的同一个 SKU，断言恰好 30 个成功、`reserved_qty` 恰好等于 30、`-race` 无报告。**改防超卖那段代码后必须重跑这条测试**，它是唯一能验证"条件更新真的原子"的手段。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| `besdk.Consume` 给 `fn` 的 `tx` 上执行"不带 schema 前缀"的 SQL 报 `relation does not exist` | `Consume` 早期签名（`be-sdk-go` ≤ v0.1.7）只 `BeginTx`，没有像 `WithTx` 那样 `SET LOCAL ROLE`+`search_path`——本组件是第一个真的调用 `Consume` 的组件，一用就撞上 | 已在 `be-sdk-go@v0.1.8` 修：`Consume` 加 `role` 参数，内部做和 `WithTx` 一样的两条 `SET LOCAL`。升级 `go.mod` 依赖即可，业务代码不用改写法 |
| `inventory_movements` 的月分区维护任务（`monthly.go`）尝试新建一个和已有分区**时间范围完全重叠**的分区，报 PostgreSQL"分区范围不许重叠" | 迁移里手写的初始分区名（`inventory_movements_2026_09`）和 `ensurePartition` 生成的命名格式（`表名_YYYY_MM_01`）不一致，`to_regclass` 查不到已有分区，误判"不存在" | 统一成 `表名_YYYY_MM_01` 格式（月初那一天）。**教训记进设计计划 §9 第 8 条**：任何"迁移建初始分区 + 后台任务建后续分区"的表，两处必须共用同一套命名格式 |
| 手动伪造过一次"先 SELECT 查够不够、再 UPDATE 扣"的写法 | 两条语句之间有窗口，`TestReserve_并发防超卖` 在这种写法下真的报了"预期成功或 ErrInsufficientStock，实际是别的错误"——数据库层的 `inventory_balances_no_oversell` CHECK 拦住了最终数据（防线仍然生效），但判定逻辑本身已经错了；这是实现时做的对照实验，不是生产事故 | 条件必须写在 `UPDATE` 的 `WHERE` 里，判定与加锁是同一条语句（§2.2） |
